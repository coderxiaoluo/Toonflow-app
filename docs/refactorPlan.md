# Toonflow 项目系统重构方案

| 项 | 内容 |
| --- | --- |
| 文档性质 | 公司内部立项与实施依据 |
| 适用对象 | 产品、研发、运维、安全 |
| 目标形态 | 部署在公司服务器上的 Web 产品。模型由公司预先接好，用户登录后直接使用 |
| 架构结论 | 模块化单体。生成与转码用同仓库的 worker 进程，不拆微服务 |
| 规模口径 | 第一年按注册 500、日活 150、峰值同时在线 40 设计。数字变了，只改机器规格，不改架构 |
| 周期 | 约 16 周，2～3 名后端/全栈 + 1 名前端，可兼职运维 |

本文只覆盖重构范围。画布交互、节点种类、Agent 能力沿用现有产品，不在本期重做。

---

## 1. 项目背景

Toonflow 是 AI 短剧、漫剧和视频创作工具。创作者在无限画布上摆放文本、图片、视频、音频节点，把节点连成工作流，由模型生成画面、视频和声音，再由 Agent 协助写分镜和改稿。

当前仓库是官方桌面/本地版的 fork，运行方式是：

- 浏览器或桌面壳连本机 Express 服务。
- 项目就是用户自己选的一个文件夹。画布是带 `toonflowCanvas` 标记的 JSON，素材是文件夹里的文件。
- 设置写在数据目录的 `settings.json`，整份覆盖保存。
- 服务是单进程。文件锁在进程内，不能多进程同时写同一个工作区。
- 语言模型和媒体模型由使用者自己填写供应商密钥。官方渠道 `api.toonflow.net` 负责账号、插件市场、余额和探索社区。
- 「多租户」设置页仍是开发中占位，没有组织、项目权限和服务器端账号。

这套形态适合个人在自己电脑上创作，不适合公司把产品部署到服务器、让一批用户打开网页就用。主要差距有四条：

1. 数据在每个人的磁盘上，不能集中备份、审计和交接项目。
2. 模型密钥分散在使用者本地，公司无法统一采购、限流和算清成本。
3. 没有公司自己的登录和权限。官方账号、广告、插件市场都指向外部服务。
4. 单进程加本地文件锁，不能直接水平扩成多台应用机。

重构要保留的是已经能用的创作面：Vue 3、Vue Flow 无限画布、现有节点（文本、图片、图片生成、视频、视频生成、音频、音频生成、抽帧分析、3D 导演）、Agent、技能和 FFmpeg。要换掉的是运行边界：从「本机文件夹 + 用户自备密钥」换成「公司服务器上的项目 + 公司接好的模型」。

市面上同类产品的共同做法，也是这次选型的参照：

| 产品 | 借鉴点 | 本期不照搬的部分 |
| --- | --- | --- |
| Figma、Miro | 项目、权限、版本历史、画布是服务器上的文档 | 多人实时光标和 CRDT。第一期没有这个需求 |
| ComfyUI 云端、Liblib 工作流 | 节点图在浏览器里编辑，重计算放服务器队列 | 允许用户上传任意自定义节点。服务器上这是代码执行风险 |
| Flora、Krea、Weavy | 无限画布加生成节点，模型由平台提供，用户只选模型 | 不自建模型，只接上游 |
| 即梦、可灵、海艺 | 用户不接触 API Key，按账号额度使用 | 不做他们的封闭模型，只做中转和额度 |
| tldraw、Excalidraw | 画布文档可序列化、可版本化 | 不更换现有 Vue Flow 编辑器 |

结论：产品形态靠近「公司托管的 AI 创作画布」，数据形态靠近「画布 JSON + 对象存储里的媒体」，运行形态保持一个应用服务。

## 2. 需求范围

### 2.1 本期要做

- Web 登录后使用。会话保持在服务器，关闭浏览器再打开仍在登录态。
- 组织、用户、项目。一个公司先按一个组织落地，表结构预留多组织。
- 项目内多张画布。画布文档仍使用现有 `toonflowCanvas` 结构（nodes、edges、viewport），存到数据库并保留版本。
- 图片、视频、音频等素材进对象存储。画布里只存对象键，不存本机路径。
- 模型中转。管理员配置上游地址和密钥，用户只看到模型名称、能力和剩余额度。
- 生成任务队列。图片、视频、音频、语言模型调用都落任务表，可查询、可取消、失败可看原因。
- 按人或按项目的额度，以及调用流水。
- 管理端：用户、角色、模型路由、额度、任务、审计。
- 备份、恢复和基本上线运行手册。

### 2.2 本期不做

- 桌面端和手机端作为主入口。现有桌面壳不删除，但不作为公司部署的交付物。
- 多人同时编辑同一张画布、实时光标、评论批注。
- 用户自行填写上游 API Key，或自行安装任意 UMD 节点、工具和提供方。
- 官方 Toonflow 账号、钱包、插件市场、首页广告、探索社区。
- 把 MCP、浏览器工具、本机选目录暴露到公网。
- 微服务拆分、Kubernetes、多地域容灾。
- 自研大模型。

### 2.3 用户看到的结果

用户打开公司域名，登录，进入项目列表，打开画布，选择「公司已经接好的模型」生成内容。用户看不到密钥，不需要安装桌面程序，也不需要选择本机文件夹。

管理员在后台添加同事、分配项目角色、配置上游模型、设置每人每月额度、查看谁在什么时间生成了什么。

## 3. 用户规模评估

第一年按下面这组数字设计。它描述的是一家公司自己用，或把同一套系统托管给少量客户，但第一期只跑一个组织。

| 指标 | 取值 | 依据 |
| --- | --- | --- |
| 注册用户 | 500 | 公司创作、编导、审核及相关协作人员，含预留 |
| 日活 | 80～150 | 创作工具不是全员每天使用 |
| 峰值同时在线 | 40 | 约日活的三分之一 |
| 同时打开画布 | 25 | 在线用户里约六成停在画布页 |
| 同时进行的语言模型对话 | 15 | 占用的是上游额度和连接数，几乎不占本机算力 |
| 同时图片生成 | 8 | 等待时间主要在上游 |
| 同时视频生成或转码 | 3 | 本机 CPU、内存和磁盘的实际上限 |
| 单张画布节点 | 常规 200 以内，上限按 500 校验 | 超出拒绝保存并提示拆画布 |
| 首年媒体存量 | 2～5 TB | 原片、生成结果、抽帧和封面 |

真正决定机器大小的不是注册人数，而是同时进行的视频转码路数，以及对象存储和上游模型账单。

粗算：

- 1 路 1080p 转码大约吃 2～4 个 CPU 核心和 2～4 GB 内存，持续数分钟。3 路并行就要单独留出 worker，不能跟接口进程挤在 4 核小机上。
- 画布 JSON 很小。500 个项目、每个 5 张画布、每张 1 MB，库内文档大约 2.5 GB，加上版本历史按 10 倍估算仍是几十 GB 量级，数据库压力不大。
- 媒体才是容量和带宽的大头。100 个日活每人每天产生 200 MB 成片和预览，一个月大约 600 GB 新增，首年落到数 TB 是合理区间。
- 模型费用会明显高于服务器租金。没有额度上限时，少数用户可以在一天内花掉整个月的上游预算。额度是上线条件，不是后续优化。

超过下列任一条件时，再评估拆 worker 集群或只读副本，而不是提前拆成微服务：

- 视频类任务峰值长期高于 8 路，单台 worker 排队超过 10 分钟。
- 日活超过 500，或要按客户做故障隔离。
- 需要两个机房同时写同一批项目。

## 4. 架构选型：为什么是单体

选择模块化单体：一个代码仓库、一个主服务进程、一个 worker 进程、一套数据库。对外只有一个 Toonflow 站点。

```text
浏览器
  └─ Nginx（证书、静态资源、反向代理）
       └─ 应用进程（登录、项目、画布、权限、额度、管理端）
            ├─ PostgreSQL
            ├─ Redis（会话、队列、限流）
            ├─ 对象存储（素材和成片）
            └─ worker 进程（同一代码库：生成、下载上游结果、FFmpeg）
                 └─ 模型上游（只允许配置过的地址）
```

应用进程和 worker 是两个进程，发布物相同。这是为了把转码和长时间上游调用从接口进程里拿出去，避免一条视频任务拖死登录和保存。它不是另一个独立产品，也不单独做一套鉴权。

### 4.1 理由

1. 现有服务就是单进程 Express。工作区写入依赖进程内锁，设置是整份快照。先把数据从本机文件夹搬进数据库和对象存储，比先拆服务边界收益大。
2. 一次「生成并写回画布」要同时动任务、额度、对象存储和画布版本。放在一个数据库事务和同一套权限里，失败可以回滚额度。拆成用户服务、画布服务、计费服务之后，这次操作变成分布式事务。
3. 慢的部分在上游模型和 FFmpeg，不在接口路由。加机器时应加 worker，而不是把登录接口单独部署。
4. 第一期明确不做 Figma 那种多人实时协同，就不需要协同网关、CRDT 服务和冲突服务。
5. 以 2～4 人维护一套对外服务，单体的发布、日志、备份和排障都在一条链路上。微服务会把同一条故障拆进多个仓库和多个仪表盘。
6. 模块按目录分开（账号、项目、画布、素材、任务、模型、审计）。以后若视频任务必须独立扩容，worker 已经是单独进程，沿队列加机器即可，应用代码不用先重写。

### 4.2 不选微服务的边界

下面这些情况出现后再拆，现在不做：

- 某个客户要求数据与其他客户物理隔离。那时按组织拆数据库，而不是按功能拆服务。
- worker 需要扩到多台，且队列已经成为稳定契约。这一步仍然保持同一个代码库。
- 管理端的发布节奏必须和创作端分开。当前管理端用户很少，没有这个必要。

### 4.3 模块划分

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| 接入 | 证书、静态文件、登录态、限流 | 业务规则 |
| 账号与组织 | 用户、会话、角色 | 项目内细粒度权限 |
| 项目与画布 | 项目、画布文档、版本、编辑锁 | 媒体转码 |
| 素材 | 上传、签名读取、生命周期 | 画布节点逻辑 |
| 任务 | 入队、状态、取消、写回节点 | 直接保管上游密钥 |
| 模型中转 | 上游路由、密钥、请求改写、用量回传 | 用户可见的密钥管理 |
| 额度 | 冻结、结算、拒绝超额 | 调用上游 |
| 审计 | 管理操作和关键创作操作留痕 | 业务判断 |
| worker | 消费队列、调用中转、FFmpeg、回写结果 | 对浏览器直接提供页面 |

前端继续用现有 Vue 3 + Vue Flow。`useWorkspaceFiles` 从「当前项目的本机目录」改为「当前项目的服务端文件接口」。画布文件格式不改，避免重写节点。

## 5. 登录

第一期用邮箱加密码。会话放在 HttpOnly Cookie 里，不把长期令牌交给前端脚本。企业微信或飞书登录放到额度和画布稳定之后，避免两套身份同时开工。

### 5.1 流程

```text
打开站点
  → 无会话：登录页
  → 提交邮箱和密码
  → 服务端校验密码哈希、账号状态、登录失败次数
  → 建立服务端会话，写 Cookie
  → 进入该用户有权限的项目列表

以后增加 SSO 时：
  → 跳转企业身份源
  → 回调拿到稳定的外部用户 ID
  → 绑定到已有用户或由管理员预先开通的账号
  → 同样建立服务端会话
```

### 5.2 规则

- 密码只存哈希（Argon2id 或 bcrypt），不可逆。
- Cookie：`HttpOnly`、`Secure`、`SameSite=Lax`，会话 7 天，空闲 12 小时失效。退出登录时服务端删除会话。
- 同一账号连续失败 5 次，锁定 15 分钟。锁定只针对该账号，不锁 IP 段，避免公司出口 IP 互相影响。
- 管理员创建账号或发送邀请，第一期不开放公开注册。公司系统不需要陌生人自助开通。
- 首次登录强制修改初始密码。
- 管理员可停用账号。停用后会话立即失效，进行中的任务允许跑完或按策略取消，二选一并写进运行手册。建议：停用后不再接收新任务，已入队任务完成，避免白扣上游费用又没有结果归属。
- 不接入 `api.toonflow.net` 的登录。公司用户和官方社区账号分开。

### 5.3 为什么不用「前端保存 JWT 一周」

无状态 JWT 在退出登录、停用账号、改权限时难以立刻失效。公司场景里停用是刚需，所以会话存在 Redis，请求时能废掉。访问令牌若以后要给移动端，再发短时令牌，不改变「服务端可吊销」这个前提。

## 6. 权限设计

两层：组织角色决定能不能管人和模型；项目角色决定能不能看和改某套画布。模型密钥不属于任何项目角色。

### 6.1 角色

| 角色 | 范围 | 可以做的事 |
| --- | --- | --- |
| 平台管理员 | 整个站点 | 管组织、上游模型、全局额度、审计、备份相关操作 |
| 组织管理员 | 一个组织 | 管本组织用户、项目、项目成员、本组织额度 |
| 成员 | 组织内 | 只能进入被授予的项目 |
| 项目所有者 | 一个项目 | 改项目名称、成员、删除项目、编辑画布、生成 |
| 项目编辑 | 一个项目 | 编辑画布、上传素材、发起生成 |
| 项目查看 | 一个项目 | 打开画布和预览素材，不能改、不能生成 |

平台管理员默认不浏览创作内容。排查问题需要查看某个项目时，走单独的「临时查看」动作并记审计，不做成隐式超管可读全部成片。

### 6.2 编辑锁

同一张画布同时只允许一个编辑者写入。其他人可以只读打开。

- 打开编辑时获取锁，租约 60 秒，前端每 20 秒续期。
- 锁的持有者掉线，租约到期后其他人可接管。
- 保存必须带当前版本号。版本不一致则拒绝写入，前端提示刷新，避免静默覆盖。
- 查看角色不能拿锁。

这是单人编辑加乐观版本，不是实时协同。参照 Figma 的是权限和版本，不是多人光标。

### 6.3 模型和额度

- 只有平台管理员能新增、停用上游和填写密钥。
- 编辑者只能在已发布的模型列表里选择。
- 生成前冻结额度，成功后按实际用量结算，失败且没有上游计费时解冻。上游已经计费但结果下载失败，记为已消耗并保留任务错误，不假装没花钱。
- 额度可以按组织总量和按人限额同时存在。先碰到的上限生效。

### 6.4 接口检查顺序

每个写操作按这个顺序拒绝，缺少任何一步都不执行业务：

1. 会话有效，用户未停用。
2. 组织角色或项目角色满足动作。
3. 资源属于该组织，不能用别的组织的 ID 越权。
4. 额度、锁和版本号满足写入条件。

## 7. 数据库设计

PostgreSQL 存结构化数据。画布正文第一期放在数据库的 JSON 列里，单张文档上限 2 MB。媒体文件不进数据库，只存对象键。Redis 只放会话、分布式锁、限流计数和任务队列，不作为业务数据的唯一副本。

### 7.1 表

```text
user
  id, email, name, password_hash, status, created_at, disabled_at

session
  id, user_id, expires_at, revoked_at, ip, user_agent

organization
  id, name, status

membership
  organization_id, user_id, role          -- admin | member

project
  id, organization_id, name, owner_user_id, created_at, archived_at

project_member
  project_id, user_id, role               -- owner | editor | viewer

canvas
  id, project_id, name, revision, document, updated_by, updated_at
  -- document 即现有 { toonflowCanvas, nodes, edges, viewport }

canvas_revision
  id, canvas_id, revision, document, created_by, created_at
  -- 每次成功保存追加。保留最近 50 版，更早的只留每日一版，保存 90 天

asset
  id, project_id, object_key, media_type, bytes, sha256, created_by, created_at

generation_task
  id, project_id, canvas_id, node_id, user_id
  kind                  -- language | image | video | audio | ffmpeg
  model_route_id, status, error_message
  quota_frozen, quota_settled
  result_asset_id, created_at, finished_at

model_route
  id, name, kind, upstream_base_url, secret_ref, enabled, config
  -- secret_ref 指向密钥存放位置，表内不写明文密钥

quota_account
  id, subject_type, subject_id, period, limit_amount, used_amount
  -- subject 可以是 organization 或 user

quota_ledger
  id, quota_account_id, task_id, amount, action, created_at
  -- action: freeze | settle | release

audit_log
  id, actor_user_id, action, target_type, target_id, detail, created_at
```

`model_route.config` 放模型能力、默认参数和价格系数，不放密钥。密钥放环境变量或服务器上的密钥文件，数据库只存引用名，例如 `ARK_KEY`。第一期上游数量少，这样做比引入单独的密钥管理系统简单，同时避免备份数据库就等于备份全部密钥。

### 7.2 约束

- `user.email`、`session.id` 唯一。
- `membership` 的 `(organization_id, user_id)` 唯一。
- `project_member` 的 `(project_id, user_id)` 唯一。
- `canvas.revision` 从 1 递增。保存时 `where revision = 客户端带来的版本`，更新行数为 0 则返回冲突。
- `generation_task.status` 只允许：排队、运行、成功、失败、已取消。
- 删除项目是归档，不物理删除画布和素材。物理清理走单独的、有确认的保留期任务，不在普通删除接口里做。

### 7.3 画布和素材怎么对应

现有本地目录里的 `画布1.json` 和旁边的图片文件，迁到服务器后变成：

- 一行 `canvas`，文档结构不变。
- 节点里的本地相对路径改成 `asset.id`。
- 文件字节在对象存储，路径形如 `org/{orgId}/project/{projectId}/asset/{assetId}`。

读取媒体走短期签名地址，有效期 10 分钟，不把存储桶设为公开读。

### 7.4 模型中转怎么落库

用户请求只带 `model_route_id`。应用进程检查权限和额度后写 `generation_task`。worker 读取路由，拼上游请求，密钥只在 worker 内存中使用。

上游按公司已经确定要接的协议适配，现有代码里已有 DeepSeek、火山方舟、OpenAI 图片接口一类提供方，重构时把「用户自己填的 key」改成「路由上的 secret_ref」。新增上游时加适配器，不让用户填地址。

中转不做成一个对公网开放的 OpenAI 兼容代理。它只接受已经登录、而且任务表里存在的内部调用。否则这台服务器会变成任何人都能盗用的模型代理。

## 8. 部署拓扑

第一期两台云主机加托管数据库、Redis 和对象存储。应用无状态，会话在 Redis，所以应用可以是一台，以后加第二台不改代码。

```text
                    互联网
                      │
                      ▼
              ┌───────────────┐
              │ Nginx         │  证书、静态资源、请求体大小限制
              │ 应用机 A       │
              └───────┬───────┘
                      │
          ┌───────────┼────────────┐
          ▼           ▼            ▼
   ┌────────────┐ ┌────────┐ ┌──────────────┐
   │ 应用进程    │ │ Redis  │ │ 对象存储      │
   │ 登录/画布   │ │ 会话   │ │ 素材、成片    │
   └─────┬──────┘ │ 队列   │ └──────────────┘
         │        │ 限流   │
         ▼        └────────┘
   ┌────────────┐
   │ PostgreSQL │
   └────────────┘
         ▲
         │ 只通过队列和数据库通信
   ┌─────┴──────────┐
   │ worker 进程     │  应用机 B，或与 A 同机（见资源表）
   │ 生成 / FFmpeg   │
   └────────┬───────┘
            │ 仅配置过的上游域名
            ▼
     DeepSeek / 火山方舟 / 视频与图片上游
```

网络分区：

- 用户只能访问 443。
- PostgreSQL、Redis、对象存储内网访问，不对公网开放。
- worker 需要出网，但出网域名收到模型路由表里的上游，不做任意 URL 拉取。用户如果要引用外链图片，先下载进对象存储，并限制协议、大小和超时。
- 管理端和创作端同一站点、同一登录，用角色区分页面。不为管理端另开一套未保护的内网端口。

发布：构建现有 `build/server` 产物，静态页由 Nginx 托管，应用进程只提供 `/api`。回滚保留上一版构建目录，数据库变更向前兼容，先加表和列，再切换读写，不在一次发布里做不可逆的删列。

## 9. 服务器资源预估

价格会变，这里给规格。模型账单单列，不进这张表。

### 9.1 起步：一台应用机，验证公司内部能不能用

适合峰值同时在线 40 以内、视频任务不超过 2 路。

| 资源 | 规格 | 作用 |
| --- | --- | --- |
| 应用兼 worker | 8 核，16 GB 内存，系统盘 200 GB SSD | Nginx、应用进程、最多 2 路转码 |
| PostgreSQL | 2 核，8 GB，100 GB | 可用同机 Docker，正式上线前迁走 |
| Redis | 1 GB | 可与应用同机 |
| 对象存储 | 按量，先按 1 TB | 素材和成片 |
| 带宽 | 20～50 Mbps | 预览视频会顶满，内部试用可接受 |

这是试用规格。转码和接口在同一台机器上，视频任务会让保存画布变慢。只用于内部试运行。

### 9.2 正式：第一年口径

| 资源 | 规格 | 说明 |
| --- | --- | --- |
| 应用机 | 8 核，16 GB，系统盘 100 GB | 只跑 Nginx 和应用进程，可先一台 |
| worker 机 | 16 核，32 GB，数据盘 500 GB SSD | 3 路视频转码、下载上游结果、临时文件。临时盘要有清理 |
| PostgreSQL | 4 核，16 GB，200 GB，每日自动备份，保留 7 天 | 托管或单独一台，不和应用混部 |
| Redis | 2 GB，开持久化 | 会话丢了只会让用户重新登录；队列丢了会丢未完成任务，所以队列以数据库任务表为准，Redis 只做通知 |
| 对象存储 | 3 TB 起，开版本控制或回收站 | 删除进入回收站，7～30 天后再物理删除 |
| 带宽或 CDN | 应用 50 Mbps；媒体走对象存储/CDN | 成片不要经应用进程转发 |

磁盘按「临时文件峰值」留余量：3 路视频同时落地，每路源片加转码产物按 2 GB 计，临时盘至少留 50 GB 空闲。

### 9.3 什么不需要买

- 第一期不买 Kubernetes、服务网格和多可用区双活。
- 不为语言模型买 GPU。文本、图片、视频都走上游 API。
- 不把全部媒体放在应用机磁盘上。应用机磁盘只放系统和临时文件。

## 10. 安全方案

公司服务器上的主要风险不是页面被改样式，而是密钥被偷、项目被越权查看、服务器被当成开放代理，以及生成费用失控。

### 10.1 身份和会话

- 全站 HTTPS。Cookie 标志见第 5 节。
- 管理操作二次确认：停用用户、更换上游密钥、归档项目。
- 审计记录：登录失败、权限变更、模型路由变更、额度调整、项目归档、临时查看项目内容。
- 审计日志只追加，普通管理员界面不能删。

### 10.2 密钥和上游

- 上游密钥不进仓库、不进前端、不进画布 JSON、不进普通备份的明文导出。
- 模型中转拒绝未在路由表中的主机名，禁止用户传入回调地址去打内网。
- 现有「自定义供应商」设置从用户界面移除。需要新模型时由管理员加路由。
- 关闭对公网的 MCP、设备配对、本机目录选择和任意插件安装入口。这些能力默认能摸到服务器文件系统或执行插件代码。

### 10.3 数据和上传

- 所有项目查询带 `organization_id`，防止用枚举 ID 读到别人的画布。
- 上传限制：图片、视频、音频、常见文档；单文件大小按类型封顶（图片 30 MB，视频 500 MB，其他 20 MB，可按业务改，但必须有上限）。
- 画布保存限制文档大小和节点数量。
- 签名地址短时有效，且签名与项目权限在签发时再查一次。
- 对象存储桶禁止公共列举和公共写入。

### 10.4 费用和滥用

- 每人同时运行的任务有上限：语言 2、图片 2、视频 1。超出排队，不无限打上游。
- 组织月额度耗尽后，生成接口直接拒绝。
- 单任务最大等待时间：语言 2 分钟，图片 5 分钟，视频 20 分钟。超时标失败并停止继续重试。视频是否已在上游扣费，按该上游的查询接口核对一次，不能盲目重试三次。

### 10.5 主机和备份

- 服务器只开放 22（限管理 IP）和 443。数据库端口不对公网。
- 系统账号分开，应用不用 root 跑。
- PostgreSQL 每日备份，对象存储开启回收站。每季度做一次恢复演练：备份能否拉起，随机一个项目的画布和成片能否打开。
- 依赖和镜像固定版本。不在生产机上临时 `bun install` 未锁定的包。

### 10.6 内容与合规

生成内容的版权和人物、商标风险由使用制度约束，不在这个重构里做完整审核平台。第一期至少做到：任务留存发起人、时间和模型；管理上可按人导出记录。若公司要求先审后发，再加「成片默认私有，分享需审核」状态，表上可先留 `asset.visibility`，默认 private。

## 11. 实施排期

按 16 周估算。前提是画布前端继续用现有 Vue Flow，只换保存位置和登录。若中途要改节点交互或上实时协同，后面的周数无效。

| 阶段 | 时间 | 产出 | 完成标准 |
| --- | --- | --- | --- |
| 0. 边界冻结 | 第 1 周 | 本文档确认、上游模型清单、额度规则、不做清单 | 产品确认本期不接官方账号、不做实时协同、不开放自定义 Key |
| 1. 身份和项目壳 | 第 2～4 周 | 登录、会话、组织、项目成员、空项目页 | 两人账号互不可见对方项目；停用立即掉线 |
| 2. 画布和素材上云 | 第 5～8 周 | 画布按版本保存、编辑锁、上传和签名预览 | 现有节点在服务器项目里能摆放、连线、刷新后还在；冲突保存不会覆盖新版本 |
| 3. 模型中转和任务 | 第 9～12 周 | 管理员配置路由、额度冻结与结算、worker 回写节点 | 用户不填 Key 能完成一次图片或文本生成；失败不重复扣费；视频至少接通一条上游 |
| 4. 上线 | 第 13～16 周 | 审计、备份恢复演练、正式规格部署、旧本地项目导入工具 | 按第 9.2 节部署；从备份恢复一个项目；一份本地画布文件夹能导入 |

导入工具只保证：一个本地项目文件夹里的画布 JSON 和其引用的图片视频能进一个服务器项目。对话记录、本机插件、个人设置不迁移。

每阶段结束都可以停下来给内部试用。第 2 阶段结束还不能生成，但已经能把项目从个人电脑里挪走。不要在模型中转完成之前对全员切换，否则用户会认为系统坏了。

人员：后端负责表结构、权限、任务和 worker；前端负责登录、项目列表和把工作区文件接口换到项目接口；同一人可以兼任，但第 2 阶段和第 3 阶段不要并行改同一条保存链路。

## 12. 风险点

| 风险 | 表现 | 处理 |
| --- | --- | --- |
| 上游费用失控 | 上线几天账单异常 | 没有额度上限不准上线；视频并发默认 1；密钥只放服务端 |
| 中转被当成开放代理 | 未登录或任意 URL 打到内网和上游 | 中转只接受内部任务；主机名白名单 |
| 画布覆盖 | 两人先后保存，后保存的冲掉先保存的 | 版本号冲突拒绝写入；编辑锁减少发生次数 |
| 本地项目迁不完 | 节点里存了绝对路径或缺失素材 | 导入报告列出缺文件，不假装成功；路径只认项目内相对路径 |
| 视频拖死接口 | 转码占满 CPU，保存超时 | 正式环境 worker 单独机器；试用环境限制 1 路 |
| 插件代码执行 | 沿用现在的任意 UMD 安装，等于让用户在服务器上跑代码 | 第一期只发布仓库里的内置节点和工具 |
| 跟官方仓库分叉 | 上游画布改动难以合并 | 少改节点组件，把变化集中在存储、登录和模型配置这三处 |
| 单进程假设残留 | 开两台应用后，内存锁失效，写坏画布 | 锁和队列改到 Redis 和数据库。在第二台应用机加入前完成，不靠约定「先只开一台」长期顶着 |
| 删除误伤 | 归档项目时顺手删掉对象存储成片 | 普通删除只归档。对象物理删除单独做，带保留期 |
| 密钥进备份 | 数据库或 settings 备份泄露全部上游 Key | 密钥不入库、不进 settings.json |
| 范围膨胀 | 协同、社区、桌面、手机一起做 | 第 2.2 节的清单作为变更门槛。要加，就加周数和人手，不挤进当前 16 周 |
| 合规 | 成片含肖像或未授权素材 | 默认私有；留发起人和时间；分享策略由公司另行规定 |

## 13. 上线前检查

- 未登录访问任何项目接口都得到拒绝。
- 查看角色不能保存画布，也不能创建生成任务。
- 用另一个组织的项目 ID 访问，结果与项目不存在相同。
- 用户界面和接口响应里都没有上游密钥。
- 额度用尽后新任务被拒绝，已冻结未结算的任务状态正确。
- 画布版本冲突能返回明确错误，刷新后看到的是新版本。
- 备份恢复后，抽查项目的画布和至少一个视频能打开。
- MCP、本机选目录、自定义供应商、任意插件安装在公网站点上不可用。
